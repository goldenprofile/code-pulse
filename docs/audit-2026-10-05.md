Дата: 2026-10-05
Фреймворк: нет (stdlib: `http.server` + `sqlite3` + `ProcessPoolExecutor`), фронтенд — vanilla JS + Chart.js
Размер: 13 Python-файлов (~2 000 строк), web — ~1 150 строк (app.js 798, index.html, styles.css)
Контекст: локальный однопользовательский инструмент на 127.0.0.1, не прод-сервис. Оценка сделана с этой поправкой.

## Итоговый балл: 5.4/10 — MVP-уровень

Ядро аккуратное и работает, но метрики, ради которых проект существует, местами считаются
неверно, а тестов, которые бы это поймали, нет совсем. Плюс одно обещание README
(«ежедневный снапшот — график достраивается сам») кодом не выполняется.

## Критичные проблемы

### 1. История не «достраивается сама» — README обещает то, чего код не делает
`scanner.py:307` пишет живой снапшот всегда с `commit_id="WORKTREE"`, а `store.save_snapshot`
делает upsert по `(project, commit_id)`. Значит на проект существует ровно **один** worktree-снапшот,
он перезаписывается при каждом скане. Новые точки истории появляются только из бэкфилла git-деревьев,
а бэкфилл запускается лишь при пустой истории (`run.py:89`), при включении проекта в ⚙ или по кнопке
в UI. В текущей БД: 59 исторических снапшотов, все датированы 2026-09-15 и раньше, + 35 WORKTREE.
README: «При каждом старте в фоне обновляется живое состояние и пишется ежедневный снапшот — график
достраивается сам».

Исправление (одно из):
- писать снапшот с ключом `f"WORKTREE:{date.today()}"` (по одному на день), а `ts` брать текущий;
- или в стартовом `run_refresh` после скана вызывать инкрементальный `scanner.backfill` (деревья,
  уже посчитанные, пропускаются через `has_snapshot`, так что это дёшево).

### 2. JS-анализатор считает каждый `if`/`for`/`while` функцией
`metrics_js.py:17-19`: в третьей альтернативе `_FUNC_RE` перед `(\w+)` нет `\b`, поэтому негативный
lookahead обходится сдвигом на один символ: `if (x) {` матчится как метод `f`, `while (` как `hile`,
`for (` как `or`. Проверено: функция с одним `if`, одним `for` и одним `while` даёт `funcs=4, cc=8`
вместо `funcs=1, cc=4`. Тело вложенного блока ещё и считается повторно внутри тела родителя.
Следствие: `funcs`, `cc`, `cog` и MI всех JS/TS-проектов искажены, а `cog_per_func` (подындекс
сложности в скоре) занижен — JS-проекты выглядят лучше, чем есть.

Исправление: `r"|(?:async\s+)?\b(?!(?:if|for|while|switch|catch|function|else|do|return)\b)(\w+)\s*\([^)]*\)\s*\{"`
и юнит-тест на этот кейс.

### 3. Нет защиты от CSRF и DNS rebinding у локального API
`server.py:377-401` принимает POST без проверки `Origin`/`Host`/`Content-Type`; тело парсится как JSON
при любом `Content-Type`. Любая открытая в браузере страница может отправить «простой» запрос
(`text/plain`) на `http://127.0.0.1:8787/api/backfill` с `{"days": 100000}` (запуск тяжёлого
бэкфилла по всем репозиториям, `days` не ограничен), или переключать исключения через
`/api/settings/exclude`. Через DNS rebinding чужой сайт может ещё и **прочитать** `/api/overview`:
пути проектов, ветки, сообщения коммитов, имена незакоммиченных файлов.

Исправление (около 10 строк): в `do_GET`/`do_POST` отклонять запрос, если `Host` не
`127.0.0.1:<port>`/`localhost:<port>`; в `do_POST` дополнительно требовать
`Content-Type: application/json` (это превращает запрос в непростой, с preflight, который сервер
не обслуживает) и проверять `Origin`, если он есть. Ограничить `days` в `/api/backfill` до 1..365,
как уже сделано в `/api/report`.

## Рекомендации

Важное:

4. **Гонка при первом запуске** — `run.py:83-93`. Фаза `scan` выставляется уже внутри потока
   (`scanner.py:269`), а `console_status()` вызывается сразу после `start()` и может увидеть ещё
   `idle`: ожидание завершится мгновенно, и бэкфилл стартует параллельно со сканом — два пула по 6
   процессов одновременно. Та же причина у `do_POST` (`server.py:379`): двойной клик по «Обновить»
   до того, как поток успел сменить фазу, запускает два скана. Исправление: атомарный
   `Status.try_begin(phase) -> bool` под локом, вызывать его до старта потока.
5. **WORKTREE и история считаются по разным наборам файлов.** `collect_worktree_files` обходит
   диск без учёта `.gitignore` (сюда попадают, например, игнорируемые `data/ui_smoke.py` и
   сгенерированные скрипты), а исторические точки берутся из `git archive`. Последняя точка графа
   систематически отличается от предыдущих — это даёт ложные `delta7` и ложные алерты деградации.
   Исправление: для git-репозиториев брать список файлов через
   `git ls-files -co --exclude-standard`.
6. **Счётчик TODO ловит идентификаторы** — `metrics_py.py:269`, `metrics_js.py:57`: `"TODO" in ln.upper()`
   срабатывает на `todos = ...`, `todo_per_kloc` и т.п. (проверено: две строки с переменной `todos`
   дают `todos=2`). Code Pulse штрафует сам себя. Исправление: regex по комментариям,
   `re.compile(r"(#|//|/\*).*\b(TODO|FIXME)\b")`.
7. **Метрика `long_funcs` — это не функции.** `metrics_py.py:353` считает **файлы** с суммарной
   когнитивной сложностью ≥ 20, а в README и UI это «длинные функции». Либо считать по функциям
   (сложность уже вычисляется в цикле `analyze_python_file:275`), либо переименовать.
8. **Дублирование завышено примерно вдвое относительно описания.** Докстринг `duplication.py:3`:
   «Первое вхождение блока не считается дубликатом», а код (`duplication.py:44`) помечает все вхождения
   окна с `count >= 2`, включая первое. Привести в соответствие код или документацию; вес подындекса
   в скоре 15%.
9. **`do_POST` без обработки ошибок** — `server.py:377`. Невалидный JSON или `"days": "x"` бросают
   исключение за пределами `try`: клиент получает сброс соединения вместо 400. Обернуть как `do_GET`.
10. **Мёртвый код и вводящий в заблуждение докстринг.** `mi_via_radon` не вызывается, а докстринг
    модуля (`metrics_py.py:7`) утверждает, что MI считается через radon, если он установлен.
    Удалить функцию и поправить текст, удалить `gitstats.activity_dates` (её логика продублирована
    в `server.py:201-204`, там же импорт `datetime` внутри цикла).

Nice-to-have:

11. `overview()` и `graph()` на каждый запрос читают и парсят полный JSON всех снапшотов, включая
    карту файлов (сейчас 94 снапшота / 5 МБ, 53 мс — нормально). Поскольку история растёт, стоит
    хранить `files` отдельной колонкой или таблицей и не тянуть её в обзор.
12. `graph()`: при протухшем кэше несколько параллельных запросов одновременно запускают

13. `_static` (`server.py:603`): проверка через `startswith` по строке пропустит соседний каталог
    `web-*`; надёжнее `path.is_relative_to(WEB_DIR.resolve())`. `GET /.` → `read_bytes()` по каталогу →
    500; добавить `path.is_file()`.
14. `load_config` (`run.py:42`) молча игнорирует битый `config.json` — пользователь не узнает, что
    его настройки не применились. Выводить предупреждение.
15. Разнести `server.py` (627 строк): сборку markdown-отчёта (`_report`, ~130 строк) вынести в
    `pulse/report.py`, `App` — в `pulse/app.py`; `scanner.live_state` (CC 34) разбить на парсер

## Сильные стороны

- Ноль внешних зависимостей: stdlib + вендорный Chart.js. Нет supply-chain-риска, ставится одной командой.
- Чистое разделение: чистые функции метрик (`metrics_py`, `metrics_js`, `coupling`, `duplication`,
  `gitstats`, `score`) отделены от I/O (`scanner`, `store`, `server`). Это идеальная база для тестов.
- Бэкфилл через `git archive` без checkout, в пуле процессов, с пропуском уже посчитанных деревьев.
- Аккуратная конкурентность SSE: подписчики под локом, `put_nowait` с дропом, `unsubscribe` в `finally`,
  keep-alive-пинги, фолбэк на поллинг на фронте.
- XSS закрыт системно: всё, что идёт в `innerHTML`, проходит через `esc()`; заголовок
  `Content-Disposition` защищён slug-ом; SQL везде параметризован.
- Сервер слушает только `127.0.0.1`; `git` вызывается списком аргументов без shell, с таймаутами.
- Хорошие README и CHANGELOG по Keep a Changelog, Conventional Commits в истории.

## Детали по каждому испытанию

### 1. Архитектура — 7/10
Слои читаются: `pulse/*` — расчёт, `scanner` — оркестрация, `store` — SQLite, `server` — HTTP.
Минусы: `App` (бизнес-логика API, кэш, SSE-шина, управление потоками) живёт в `server.py` вместе с
обработчиком и генератором markdown-отчёта — файл 627 строк, MI 23.7. `Status` в `scanner.py`
импортирует `threading` через `__import__` (`scanner.py:241`). `analyze_js` импортирует приватный
`_totals_from_reports` из соседнего модуля внутри функции — общий агрегатор стоит вынести.

### 2. Обработка ошибок — 6/10
Широкие `except Exception` осознанные и фиксируют ошибку в `Status.error`; `try_git` корректно гасит
`GitError`/`TimeoutExpired`/`OSError`. Проблемы: `do_POST` без `try` (п. 9), молчаливый битый конфиг
(п. 14), в бэкфилле `Status.error` перезаписывается каждой новой ошибкой — видна только последняя.

### 3. Безопасность — 6/10
Для локального инструмента базис хороший (bind на loopback, `esc`, параметризованный SQL, git без
shell). Снижение — за CSRF/DNS rebinding (п. 3): это реальный вектор для любого localhost-сервиса,
а API отдаёт пути и содержимое рабочих копий всех проектов.

### 4. Производительность — 7/10
На текущем объёме всё быстро (`overview` — 53 мс, ответ 67 КБ). Риски роста: полный JSON снапшотов
в каждом обзоре (п. 11), конкурентный пересчёт графа (п. 12), квадратичный проход по скобкам в
`analyze_js_file` (для каждого совпадения — поиск конца тела от его начала) — на больших бандлах
это заметно, частично сглажено `looks_generated` и `MAX_FILE_BYTES`.

### 5. Тестирование — 1/10
В репозитории нет ни одного теста. `data/ui_smoke.py` (Playwright) лежит в игнорируемом каталоге
и в историю не попадает. При этом весь расчётный слой — чистые функции, которые тестируются без
моков и без БД. Найденные баги метрик — прямое следствие отсутствия тестов.

### 6. Инфраструктура — 3/10
Нет `Makefile`, CI, `tests/`; в `pyproject.toml` только конфиг ruff, без mypy/pytest и без
`[project.scripts]`. Поскольку это локальный инструмент без деплоя, Docker и systemd не нужны —
балл не занижался за их отсутствие. Lockfile при нулевых зависимостях тоже не нужен.

### 7. Качество кода — 7/10
Pylint 9.66, стиль однородный, комментарии по делу. Минусы: 5 функций со сложностью D/E, 22 ошибки
mypy (типы в `_git_cache`, сужение `ast`-узлов), 2 мёртвые функции, смешение `typing.Dict` и `dict`
(UP006 — 45 мест, автоисправимо).

### 8. Документация — 6/10
README подробный и полезный, CHANGELOG ведётся. Снижено за расхождения документации и кода:
ежедневные снапшоты (п. 1), MI через radon (п. 10), «длинные функции» (п. 7), «первое вхождение»
в дублировании (п. 8).
